# Рішення

**VP — самостійний продукт із власним каталогом і власними скриптами** пошуку та
використання інструкцій. Канонічний корпус живе у VP; скрипти `catalog.tags` /
`catalog.search` / `catalog.get` / `catalog.compose` — детерміновані й реалізовані
в коді VP. Якщо VP встановлено окремим плагіном, він працює зі своїм скілом
запуску (Router) і своїм хуком, без залежності від VIDA Runtime.

**Якщо інструкції VP збираються в пакет поставки агента, пакет агента мусить мати
свій розширений instruction registry** — окремий реєстр у складі пакета агента, з
розширеним набором полів VP, який читається існуючим механізмом активації.

# Два режими, одне джерело

| Аспект | Standalone: VP окремим плагіном | Bundled: VP у пакеті агента |
|---|---|---|
| Каталог | `packages/powers/instructions/` — канонічний, необмежений | Той самий корпус, зібраний у пакет агента як **згенерований артефакт із декларованим Source-зв'язком** (не друга канонічна копія) |
| Пошук і використання | Власні скрипти VP (`catalog.*`) | Ті самі скрипти VP + реєстр пакета агента |
| Активація інструкцій | Власний механізм VP (Router формує bundle) | Розширений instruction registry пакета агента |
| Залежність від Runtime | Немає | Є — реєстр і його активація живуть у пакеті агента |

# Розмежування каталогу й реєстру (rev 2)

**Канонічний каталог VP (rev 2, затверджено власником 2026-10-19).** Джерелом
правил є **`.md`-інструкції з метаданими** у плоській теці `instructions/`; машинним
файлом каталогу є `catalog.json` — ідентичність, словник тегів, аліаси тегів і
записи винятків. Окремих директорій за донорами немає: джерело, ліцензія й ревізія
живуть у метаданих інструкції. Дизайн — `docs/catalog-design.md`.

Нижче — модель, ухвалена в rev 1; rev 2 змінює лише **фізичну форму каталогу**,
не межі з реєстром пакета агента і не режими доставки.

- **Каталог (канон)** — `VPCatalog/v1`: `instruction_id`, `capability_tags[]`,
  `pattern_tags[]`, `conditions`, `artifact_contract`, `compatibility`
  (групи/виключення/залежності), `provenance` (донор, ліцензія, ревізія джерела),
  `revision`, `status`, `content`. Ліміту на кількість записів немає: корпус
  виростає за обсягом донорів.
- **Реєстр пакета агента (розширений)** — власна схема й власна секція конфігурації
  в складі пакета агента, з розширеним набором полів VP. Реєстр `research_decision`
  (`InstructionRegistry/v1`) **не** змінюється і не обмежує VP: його ліміт
  `maxItems: 64` і прив'язка до research/synthesis-стадій залишаються чужою VP
  справою.
- **Один activation engine.** Розширений реєстр пакета агента не вводить окремої
  активації: розв'язання, дайджести, `privacy`, `max_bytes`, перевірка
  `output_schema` і запис activation-історії — ті самі, що вже є в runtime.
  Додавання реєстру — це runtime work item (власник: agent maintainer), а не
  ініціатива VP.

# Що це означає для репозиторію

1. **Runtime work item** (власник — agent maintainer): додати в пакет агента
   розширений instruction registry (схема + секція конфігурації + читання в
   наявному resolver'і). VP не редагує `packages/agent` сам; натомість VP постачає
   формат і збірку, runtime — реєстр і активацію.
2. **Спір про `source_path` знімається**: VP-записи не потрапляють у
   `research_decision.registry.instructions.N` (жорсткий шаблон шляху), а йдуть у
   власну секцію реєстра пакета агента.
3. **Збірка в пакет** — build-time крок із декларованим Source-зв'язком і digest,
   за наявним у репозиторії патерном згенерованих артефактів (`payload-source-provenance`).
   Канонічна копія лишається в VP.
4. **Standalone-постачання** не потребує жодних змін у runtime: VP має власні
   скрипти, скіл запуску і хук; встановлення йде через канал D4.
5. **Спільна семантика**: формат каталогу, правила тегів, `catalog.*` і
   `artifact_contract` — одна семантика для обох режимів; різняться лише способ
   доставки інструкцій до виконавця.

# Розглянуті варіанти

| Варіант | Суть | Висновок |
|---|---|---|
| (a) Розширити `InstructionRegistry/v1` | Додати VP-поля в наявний реєстр research-контуру | Відхилено: ліміт 64 і прив'язка до research-стадій не підходять корпусу; зміна чужого runtime-контракту |
| (b) `VPCatalog/v1` + проекція ≤64 у наявний реєстр | Каталог окремо, частина — у research-реєстрі | Відхилено: прив'язка до research-контуру й обмеження лишаються; у standalone-режимі проєктувати нікуди |
| (c) Повністю окрема VP-активація | Другий resolver і другий engine | Відхилено: суперечить research §4.8 і забороні дублювання механізмів |
| (d) Два режими: самостійний VP + розширений реєстр у пакеті агента | Канон у VP, реєстр у пакеті, одна семантика | **Прийнято** |

# Наслідки для плану

- Stage 2: `VPCatalog/v1` + власні скрипти `catalog.*` + специфікація розширеного
  реєстра пакета агента + runtime work item; `research_decision.registry` не
  торкається.
- Stage 3: корпус пишеться в канонічний формат каталогу; збірка в пакет агента —
  окремий крок із provenance.
- Stage 5: Router працює поверх власних скриптів каталогу; `vp-setup` встановлює
  плагін зі скілом запуску і хуком.
- Stage 7: VP-інструкції в Runtime-режимі активуються розширеним реєстром пакета
  агента; другий scheduler/ledger/БД не з'являється.
- D4 (канал доставки) має три канали: окремий плагін і збірка в пакет агента.
