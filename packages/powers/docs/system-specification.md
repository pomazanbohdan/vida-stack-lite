S-рівень: **що VP робить, спостережувано**. B-рівень — `business-requirements.md`,
науковий вихід — `research/vida-powers-product-research.md`. Кожен пункт має стабільний
ID `SR-nn`; критерії — в `acceptance.md`. Правило research не дублюється: тут лише
нормативна поведінка.

## 1. Інструкція

- **SR-01.** Інструкція — `.md`-файл із frontmatter: `instruction_id` (kebab-case, стабільний, не перевикористовується, = ім'я файлу), `title`, `summary`, `revision` ≥1, `status` (`active`/`disabled`). Канонічні імена полів — ці; кодування полів у frontmatter і точний склад каталогу визначено в `catalog-design.md`.
- **SR-02.** Два виміри тегів: `capability_tags[]` (що зробити) і `pattern_tags[]` (яка методика). Тег ≠ агент/skill/крок/дозвіл.
- **SR-03.** Тег — kebab-case із щонайменше двома змістовними компонентами; скорочення — аліаси, канонічний тег домінує.
- **SR-04.** Активна інструкція має ≥1 capability- і ≥1 pattern-тег; відсутність закривається **явним записом-винятком із причиною**.
- **SR-05.** Кожен тег має опис у словнику каталогу; тег без опису — помилка валідації.
- **SR-06.** Обов'язкові поля: `conditions`, `artifact_contract`, `compatibility` (`excludes`, `requires`), `provenance` — **список джерел** (донор, ліцензія, ревізія, шлях); інструкція може мати кілька джерел після злиття дублікатів. Решта складені поля кодуються плоскими ключами з префіксом (`conditions_applies_when`, `artifact_contract_output_type`, `compatibility_excludes` тощо) — без вкладених map; список джерел — рядками `donor=…; license=…; revision=…; path=…`. Додатково дозволено **необов'язкові** поля `roles[]` і `products[]` — носії вимірів пошуку за роллю й продуктом (SR-10, SR-70); відсутність або порожній список означає «застосовно до будь-якої ролі/продукту».
- **SR-07.** `provenance` обов'язковий і має щонайменше одне джерело. Кожне джерело — рядок `donor=…; license=…; revision=…; path=…`; ліцензія й ревізія походять із маніфесту донорів, а `revision` **має дорівнювати** `donors.yaml[donor].head_sha`. Без provenance інструкція не приймається. Злиття дублікатів зберігає всі джерела в одній інструкції, вибирає кращу термінологію та піднімає `revision`.
- **SR-08.** `artifact_contract` обов'язковий. Для інструкцій, що виробляють результат, `artifact_contract_output_type` і `artifact_contract_verified_by` непорожні, `artifact_contract_required_data` може бути порожнім. Для настановчих (guidance) інструкцій `artifact_contract_output_type` = `none`, `artifact_contract_required_data` порожній.

## 2. Операції каталогу

- **SR-09.** `catalog.tags` → доступні capability-/pattern-теги з описами, усталений порядок; без текстів інструкцій.
- **SR-10.** `catalog.search` за набором capability-тегів, pattern-тегів, ідентифікаторів, ролі, продукту та/або умов застосування (SR-70) повертає **лише метадані** (ID, назва, короткий опис, теги, ревізія) — жодних повних текстів. Фільтри поєднуються: теги в межах одного виміру — «хоча б один», між вимірами — «і»; роль, продукт і умови — кон'юнкція.
- **SR-11.** `catalog.get` → повний текст **точно вказаної** інструкції; невідомий ID — помилка, не порожній результат.
- **SR-12.** `catalog.compose` → знайдені + обов'язкові + транзитивні залежності, після перевірки сумісності й усунення дублікатів.
- **SR-13.** Обов'язкові та залежні не відкидаються за relevance-score; ліміти реєстру research-контуру на VP не поширюються.
- **SR-14.** Конфлікт `excludes` (у будь-який бік) → помилка з назвою конфліктної пари; невідома або вимкнена залежність → окрема помилка.
- **SR-15.** Каталог = інструкції (`.md` + frontmatter) + машинний маніфест `VPCatalog/v1` (`catalog.json`: ідентичність, словник тегів, аліаси, винятки); `revision` описує вміст, версія пакета — окрема величина.

## 3. Decision Provider

- **SR-16.** `decision.evaluate`: вхід — операція, продукт, контекст задачі, теги, **вже допустимі кандидати**; вихід — обрані ID, оцінка, обґрунтування, ідентифікація провайдера, ознака й причина відмови. У v1 оцінювання **детерміноване**: операція повертає shortlist або причину відмови (немає кандидатів, невідомий candidate ID, кандидат поза допустимими, некоректний формат); семантичне оцінювання лишається за скілом (D5), зовнішній провайдер — можливість хоста.
- **SR-17.** Реалізації: master LLM агента (типово) і зовнішній провайдер, якщо його задає host-конфігурація. Прив'язки до vendor API немає.
- **SR-18.** **Agent Fallback обов'язковий:** недоступність, timeout, помилка API, некоректний формат, невідомий candidate ID, недостатня впевненість → вибір переходить до головного агента; scope, policy і validation лишаються чинними.
- **SR-19.** Fallback не замінює вибір, який належить користувачу.
- **SR-20.** Джерело рішення, обрані ID і причина fallback матеріалізуються.
- **SR-21.** Поріг relevance калібрується **per operation**; для некаліброваної операції не застосовується, результат позначається як некалібрований. Висока оцінка ≠ доказ правильності, дозволу чи завершення.

## 4. Роутінг

- **SR-22.** Роутінг = **вибір LLM** → **формування агентів** за фіксованим довідником (каталогом) → **рівень флоу** (`Full` / `Medium` / `Light` чи інший профіль).
- **SR-23.** Сформований агент отримує: роль, task contract, ефективну методологію, Work Scope, вимоги матеріалізації, посилання на артефакти.
- **SR-24.** Роутінг не компілює граф виконання: маршрут належить VIDA Core/Mastra (Runtime) або хостовому агенту (Standalone); VP дає лише опис допустимих варіантів (`workflow.options`).

## 5. Методологічний профіль

- **SR-25.** Профіль (`VPMethodologyProfile/v1`): групи вибору (`testing-sequence`, `review-strategy`, `architecture`, `delivery`), активні альтернативи, сумісні доповнення, умовні залежності. Групи та їхні альтернативи оголошуються **профілем**; інструкція прив'язується до групи своїми `pattern_tags`.
- **SR-26.** Групи незалежні; альтернативи в одній групі взаємовиключні (`test-first-development` ↔ `test-after-development`), `risk-based-testing` — сумісне доповнення.
- **SR-27.** Успадкування — явне й вибіркове за стабільними ID; неявне повне успадкування через спільний репозиторій не застосовується.
- **SR-28.** Локальне перевизначення пріоритетніше за успадковане без повторного підтвердження; два суперечливі успадковані варіанти → блок із запитом власнику.
- **SR-29.** Task-scoped override — разовий узгоджений виняток для задачі й продукту: фіксується, передається дочірнім агентам; не змінює постійний профіль, інші продукти, permissions чи security gates.
- **SR-30.** Live Inheritance: посилання на стабільні ID без version pinning; зміна поведінки = **новий pattern ID**, а не заміна під тим самим ID.
- **SR-31.** Рівень флоу, застосовність і обов'язковість (`required`/`conditional`/`optional`) — окремі властивості. `Light` не пропускає обов'язкові AC, матеріалізацію й mandatory gates; `Full` не означає виконання всіх етапів.
- **SR-32.** Ролі (Researcher, Analyst, Decision Reviewer, Requirements Specialist, Test Designer, Implementer, Automation Tester, Manual/UI Tester, Independent Reviewer, Verifier) формуються за потребою; обов'язковість ролі ≠ фактична участь. Незалежна перевірка не підміняється самоперевіркою автора.
- **SR-33.** Одна схема профілю — різні носії: Runtime → розділ у `.vida/project.yaml`; Standalone → той самий розділ у керованому YAML-блоці instruction-файлу; host shim → конфіг-файл проєкту.

## 6. Дві форми інструкції

- **SR-34.** Інструкція має дві форми: **документ** (джерело; `.md` із frontmatter) і **запис реєстру** (похідний, для активації). Запис прив'язаний до документа digest'ом.
- **SR-35.** Запис реєстру несе посилання на джерело, digest контенту, клас активації, умови (`triggers`/`phases`/`lanes`), `output_schema`, ліміт розміру, клас приватності, статус. Розходження digest'а — помилка активації.
- **SR-36.** Межі реєстру (ліміт записів, шаблон шляху, ліміти розміру) — обмеження системного реєстру, а не моделі VP; розширення під VP — окремий runtime-запит до agent maintainer.

## 7. Матеріалізація

- **SR-37.** Після змістовної операції залишається читабельний результат або явно зафіксоване оновлення наявного.
- **SR-38.** Три частини: **Content Artifact** (результат), **Artifact Reference** (ID, тип, продукт, прив'язка до scope/work, локатор, ревізія/digest, зв'язки), **Action/Event Record** (хто, коли, що зробив, перевірив, погодив або не зміг).
- **SR-39.** Перевикористовуються `ResearchResult/v1`, `ResearchSynthesis/v1`, `DecisionRecord/v1`, `AcceptanceManifest/v1`, `ImplementationScope/v1`, `WorkItem/v1`, `WorkState/v1`, `LifecycleArtifactReference/v1`, `WorkArtifactReference`; паралельних версій VP не створює.
- **SR-40.** Work Item: стабільний ID, мета, Work Scope, AC, зв'язки (`derived-from`, `informs`, `implements`, `tests`, `blocks`, `supersedes`, `changes`, `found-during`), докази. Чернетку уточнюють на місці; після прийняття scope заморожується; завершену задачу не переписують — створюють новий Work Item зі зв'язком.
- **SR-41.** Перевірка наявності/формату/digest і семантична перевірка — різні операції; обидві потрібні для закриття AC.
- **SR-42.** Handoff підтверджується лише після перевірки доступності виходу та відповідності contract'у; доказ прив'язаний до редакції, яку перевіряли.

## 8. Findings

- **SR-43.** Finding фіксує проблему, докази, джерело, продукт, зв'язок із work/scope, блокувальний вплив. Створення finding'у не авторизує виправлення.
- **SR-44.** Запис централізований: один writer; subagent'и повертають структуровані повідомлення; у Runtime запис іде через власника стану.
- **SR-45.** Дедуплікація: ідентичність → детермінований пошук (ID, fingerprint, контекст, provenance) → семантичні кандидати → перевірка еквівалентності (відтворення, контекст, докази). Збіг місця чи висока оцінка недостатні; неоднозначність не об'єднується; повторна доставка не створює події.
- **SR-46.** Історія — append-only: первинні спостереження не видаляються, об'єднання — окрема подія.
- **SR-47.** `findings` у research-документі — твердження дослідження, а не записи реєстру дефектів.

## 9. Join і Lifecycle Scope

- **SR-48.** `blocking` — батьківський етап очікує результат і його прийняття; `non-blocking` — не затримує завершення батьківського етапу. Помилки й незавершені результати фіксуються та повертаються власнику.
- **SR-49.** `non-blocking` не знижує обов'язковість: результат, потрібний для AC або gate, не може бути необов'язковим.
- **SR-50.** Lifecycle Scope: `parent`, `workflow`, `independent`. Для кожної сфери визначені власник, ідентичність, місце результату, спостережуваний стан, механізм завершення/скасування.
- **SR-51.** Старт ≠ завершення; запит скасування ≠ доказ зупинки; збережений контекст ≠ доказ триваючого виконання.
- **SR-52.** Work Scope — обсяг, Lifecycle Scope — тривалість; жодна lifecycle-модель не розширює Work Scope; у Standalone немає власної durable execution-інфраструктури.

## 10. Scope-First

- **SR-53.** Інструкції, routing і вкладені задачі обмежені Work Scope; методологія, coverage/security-міркування, relevance score і статус незалежного агента не дають права розширювати scope.
- **SR-54.** Класи знахідок: баг у межах роботи — виправляється в її межах; блокер AC поза повноваженнями — блокер і запит дозволу; сторонній баг, що не блокує, — окремий finding; покращення/оптимізація — окремий запис; за погодженою auto-fix policy стороння робота — окремо після основної.
- **SR-55.** Без standing permission пропозиція виправлення сторонньої проблеми — опційний людський цикл після основної роботи.

## 11. Операційні правила

- **SR-56.** `vp-setup` ідемпотентний: повторний запуск на незміненому вході не створює дублікатів блоків, hooks, записів чи канонічних документів.
- **SR-57.** `vp-setup` не змінює файли встановленого пакета агента; кореневий `AGENTS.md` агента генерується з шаблону пакета й не редагується.
- **SR-58.** Bootstrap передає мінімальні правила, ідентичність продукту, посилання на методологію та актуальні артефакти; весь корпус у сесію не завантажується — у сесію потрапляє лише bundle, обмежений **≤ 20 інструкціями і ≤ 64 КБ** сумарного тексту.
- **SR-59.** Перевірка активації: початок сесії, відновлення після compaction, контекст делегованого агента. Відсутність host-можливості — **обмеження**, а не еквівалентна перевірка. `vp-setup` зберігає сторонні інструкції та чинну карту джерел (SR-75).
- **SR-60.** Новий або змінений hash хука потребує native review; trust-запис не синтезується — trust GAP фіксується, а не обходиться.
- **SR-61.** Відновлення після compaction відновлює вказівники й стан, а не повторює завершені змістовні дії.

## 12. Формати

- **SR-62.** Машинні формати, які читає постачаваний код, — JSON (каталог, профілі, реєстр, робочі записи); YAML — лише людські маніфести. Виняток — формат самої інструкції: `.md` із frontmatter обмеженого YAML-підмножини (власний формат продукту).
- **SR-63.** Код, що постачається в скілах, виконується без збірки під Bun/Node/Deno: лише `node:`-модулі, без зовнішніх залежностей і без Bun-специфічних API.
- **SR-64.** Dev-інструменти VP працюють під рантаймом проєкту (Bun) і можуть використовувати Bun-специфічні API.
- **SR-65.** Один canonical owner на кожен документ і контракт; паралельні копії нормативного тексту заборонені.

## 13. Вимоги, додані валідацією раунду 3

Цей розділ додано за результатами комплексної валідації (раунд 3). Тематично
пункти належать §1, §2, §3, §5, §8, §9 — вони винесені разом, щоб не розривати
наявну нумерацію.

- **SR-66.** Мапа обробки корпусу (`VPCorpusMap/v1`, `packages/powers/corpus-map.json`)
  фіксує для кожного донора (з **зафіксованою ревізією**) і кожного файлу-носія
  результат: `converted` (одна інструкція), `split` (кілька), `merged` (ціль
  злиття, `contributed_sources` — джерела внеску), `rejected` (з `reason`).
  Конвертація ідемпотентна за (донор, ревізія, шлях): повторний прогін на тій самій
  ревізії нічого не змінює. Інструкція без запису в мапі, запис мапи на відсутню
  інструкцію та `rejected` без причини — помилки.
- **SR-67.** У межах активної задачі застосовується узгоджений **знімок**
  застосованих інструкцій; наступна задача може отримати актуальнішу сумісну
  редакцію. Змінений вхід інвалідує лише прив'язаний до нього доказ.
- **SR-68.** Зміни інструкцій класифікуються за ризиком: низький — уточнення без
  зміни контракту, автоприйняття; середній — семантична сумісність, regression eval
  і незалежний review; високий — підтвердження людиною. Зміна семантики оформлюється
  **новим pattern ID**, а не редакцією тієї самої інструкції. Прийнята редакція
  фіксує походження, авторство, перевірки й окремий запис змін.
- **SR-69.** Продукт має стабільний ідентифікатор, незалежний від шляху; спільний код
  не зводиться автоматично до методології найближчої директорії — для кожного
  охопленого продукту враховуються його політика, scope і джерела. За реальної
  методологічної варіативності вибір користувача отримується **один раз** і
  фіксується; за наявної зафіксованої політики повторно не запитується.
- **SR-70.** `catalog.search` підтримує фільтри: capability-теги, pattern-теги,
  ідентифікатори, роль, продукт і умови застосування. У результаті — лише метадані.
- **SR-71.** Виконання сценарію UI-агентом **не є** людським прийняттям: без потрібної
  відповіді людини результат лишається `awaiting-human-verification`, а не PASS.
- **SR-72.** У Standalone останній запис визначається агентом прозоро, без системи
  прав, lease чи reservation; прихований перезапис чужих змін заборонений, конфлікти
  розводяться практичними засобами хоста. Жодна модель життєвого циклу не розширює
  Work Scope.
- **SR-73.** Пошук охоплює ID, filename, title, body, тип, продукт, tags/labels і
  relations. Повнотекстовий індекс **похідний** і відновлюваний; він не дублює
  нормативні документи, а чужий нормативний документ поза `wiki_root` індексується
  за посиланням.
- **SR-74.** Будь-який агент може залучити інших агентів для власних підзадач, зокрема
  для research, аналізу, підготовки інструкції, тестування чи review. Право
  **запросити** спеціаліста не дорівнює праву **надати** йому нові повноваження.
  Workflow graph і дерево делегування — різні структури: вкладена робота не додає
  зовнішніх етапів і не оминає gates. Глибина, concurrency і ресурсні межі
  визначає власник виконання (Runtime або хост), а не VP.
- **SR-75.** `vp-setup` зберігає сторонні інструкції та чинну карту джерел; оновлюється лише
  належна VP частина інтеграції, а наявний Runtime-owned файл не перетворюється на іншого
  власника політик.
- **SR-76.** Каталог-маніфест (`catalog.json`) є **єдиним переліком корпусу**: для кожної
  інструкції — `instruction_id`, `path` і `sha256` вмісту. Файл у `instructions/`, якого
  немає в маніфесті, файл у маніфесті, якого немає на диску, і розбіжність digest —
  помилки. Маніфест пише лише конвертер (єдиний writer); runtime-скрипти лише читають.
